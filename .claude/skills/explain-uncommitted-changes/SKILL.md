# Explain Uncommitted Changes

## 목적

지금 working tree에 떠 있는 모든 변경(staged + unstaged + untracked)을 모아서, **이 프로젝트의 맥락을 모르는 동료 개발자가 PR 설명을 읽듯 따라올 수 있게** 파일 그룹 단위로 풀어 설명한다.

핵심은 "파일 N개가 바뀌었습니다" 식의 나열이 아니라, **관련된 파일들을 기능/목적 단위로 묶어** 각 묶음이 무엇을 하는지·왜 추가됐는지를 짧게 설명하는 것이다.

## 언제 트리거하나

- "지금 변경사항 설명해줘", "뭐 바꿨어?"
- "커밋 전에 어떤 작업을 했는지 정리해줘"
- "uncommitted된 거 뭐야?"
- "방금까지 한 작업 친절하게 풀어줘"
- "이 변경을 PR로 올리면 뭐라고 써?"

과거 커밋 히스토리를 묻는 게 아니라 **현재 working tree 상태**를 묻는 모든 경우.

## 절차

### 1. 변경 수집

다음을 병렬로 실행:

- `git status --short` — 어떤 파일이 어떤 상태(M/A/D/??)인지 한눈에.
- `git diff` — unstaged 변경 본문.
- `git diff --cached` — staged 변경 본문.
- untracked 파일들은 `git status`로 식별해 직접 `Read`로 본다 (diff에 안 나옴). 단, lockfile/generated 디렉터리/이미지 등 **대용량 파일은 읽지 말고 "추가됨"으로만 표시**.

`git log --oneline -5`도 한 번 확인해서, 직전 커밋들이 어떤 흐름이었는지 파악(설명에 "이전 커밋이 X였고 그 위에 Y를 쌓는 중"이라고 맥락을 줄 수 있음).

프로젝트에 `PLAN.md` / `CHECKLIST.md` / `CLAUDE.md` 같은 문서가 있고 변경이 그 계획의 특정 단계를 구현하는 중이라면, 그 단계 이름을 한 줄로 인용한다. 단 추측 금지 — 변경 사항이 명백히 그 단계에 매칭될 때만.

### 2. 파일을 "기능 단위"로 묶기

폴더 구조나 파일 종류가 아니라 **무엇을 하기 위한 변경인지**로 묶는다. 같은 기능이면 src/와 prisma/와 .env에 흩어져 있어도 한 그룹.

좋은 묶음 예:

- "Auth.js 설정" — `_lib/auth.ts`, `_lib/auth.config.ts`, `api/auth/[...nextauth]/route.ts`
- "로그인 화면 UI" — `(auth)/layout.tsx`, `(auth)/login/page.tsx`
- "헤더 사용자 메뉴" — `_components/UserMenu.tsx` + `(main)/layout.tsx` 수정
- "shadcn UI 프리미티브" — `_components/ui/{button,avatar,dropdown-menu}.tsx`
- "패키지 의존성" — `package.json`, `pnpm-lock.yaml`

나쁜 묶음 예:

- "TypeScript 파일들" (확장자 기준 — 무의미)
- "src/app/ 안의 파일" (디렉터리 기준 — 기능을 안 보여줌)
- 파일 하나하나를 별개 항목으로 (그룹의 의미 없음)

판단 기준: 그룹 제목만 봤을 때 "아 그 작업이구나" 싶으면 OK. 제목이 그냥 경로 나열이면 다시 묶는다.

### 3. 출력 형식

가독성이 최우선. 빽빽한 문단 금지, 한 파일은 한 줄로.

```
## 그룹 제목 (1~5단어)

> 이 그룹이 시스템에서 맡는 역할 — 한 줄.

- `path/to/file.tsx` (신규) — 이 파일의 역할 한 줄.
- `path/to/other.ts` (수정) — 이 파일의 역할 한 줄.
```

각 파일 줄은 **무엇을 위한 파일인지(역할)**를 적는다. 구현 방식(how)이 아니라 책임(what for).

좋은 예 (역할 중심):

- `src/middleware.ts` (신규) — `/login`이 아닌 모든 페이지에 로그인 강제하는 게이트.
- `_lib/auth.ts` (신규) — 앱 어디서든 `auth()`로 현재 사용자를 꺼내 쓸 수 있게 해주는 단일 진입점.
- `(auth)/login/page.tsx` (신규) — GitHub 로그인 버튼 하나가 있는 로그인 화면.

나쁜 예 (구현 중심·문장 길고 빽빽):

- `_lib/auth.ts` (신규) — `auth.config`를 spread한 위에 PrismaAdapter, `session.strategy: "jwt"`, jwt/session 콜백, `events.signIn`을 얹어 `handlers/auth/signIn/signOut`를 export하며 module augmentation으로 Session.user에 id/githubLogin을 노출.

→ 위 내용은 "역할"이 아니라 "내부 구조"임. 역할은 "단일 진입점" 한 마디.

한 파일에 정말 별개의 책임이 두 개 이상이면 sub-bullet 허용 (최대 3개):

```
- `_lib/auth.ts` (신규) — 인증 단일 진입점.
  - GitHub 로그인 처리 + 세션 발급
  - 첫 로그인 시 GitHub username을 우리 DB의 user row에 복사
```

규칙:

- 파일 경로는 백틱으로 감싼다.
- `(신규)`, `(수정)`, `(삭제)`, `(이름변경)` 표시.
- 그룹 헤더(`##`)와 그룹 역할(`>`) 사이, 그룹과 그룹 사이에 빈 줄을 충분히 둔다.
- 그룹이 5개 넘으면 핵심 기능 → 보조 → 부수적(lockfile/generated)순. 부수적인 건 한 줄로 압축.
- 한 줄이 100자를 넘으면 두 줄로 쪼개거나 sub-bullet으로 분리.
- 구현 디테일/함정(예: 캐스트 이유, edge runtime 분리 패턴)은 **역할 설명에 끼워넣지 말 것**. 진짜 중요하면 그룹 마지막에 별도 `*` 메모 한 줄로만:

  ```
  - `_lib/auth.ts` (신규) — 인증 단일 진입점.

  *Prisma 클라이언트 경로가 커스텀이라 `prisma as never` 캐스트 필요.*
  ```

### 4. 톤과 용어

대상은 **이 프로젝트는 모르지만 코드는 읽을 줄 아는 동료 개발자**.

- 일반적 기술 용어(미들웨어, 어댑터, JWT, OAuth, route handler, server component 등)는 그대로 쓴다. 풀어 설명하지 않는다.
- 한국어. 코드/식별자/패키지명은 원어.
- 추측·과장 금지. 코드/diff에 명확히 안 보이는 동작은 단정하지 말 것.
- "이 파일은 ~를 위한 거다"가 한 문장에 담겨야 함. 두 문장 이상 가는 순간 역할이 흐려진 신호.

### 5. 빈 경우 / 예외

- 변경이 하나도 없으면: "working tree clean입니다." 한 줄로 끝.
- 변경이 1~2개 파일뿐이면: 그룹화 없이 그냥 파일별 설명 1~2문장씩.
- 변경이 수십 개여도 그룹은 5~7개 이내로 압축. 더 잘게 쪼개면 오히려 따라가기 어려움.

## 하지 말 것

- diff 본문을 그대로 붙여넣지 말 것. 요약·해석이 이 스킬의 가치.
- "다음에 무엇을 할지" 같은 next steps 섹션 만들지 말 것. 사용자가 명시적으로 묻기 전까진 변경 사항 설명에만 집중.
- 변경 사항을 평가하지 말 것 ("좋은 패턴입니다" / "리팩토링이 필요해 보입니다"). 사실 전달만.
- 사용자가 이미 알고 있는 게 분명한 conversational context(예: 직전 턴에 "이 파일 만들자" 라고 말한 상황)에서도, 이 스킬은 처음 보는 사람용 설명이라는 점을 유지한다. 사용자가 짧게 원하면 별도 요청할 것.
